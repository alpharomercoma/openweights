# The ExecuTorch catalogue: seven families, one runtime, measured

**2026-08-31.** The second runtime went from one supported model (Qwen3) to the whole
catalogue the Hub actually publishes, and this records what was built, what was measured
on the Poco X8 Pro Max (Dimensity 9400), and what was found on the way. The parity
numbers themselves live in [backend-parity.md](backend-parity.md), regenerated by
`tools/eval/run_matrix.sh` on every rerun; this file is the why behind them.

## What "supporting a family" means here

A `.pte` is a compiled graph and a tokenizer: no chat template, no metadata, no EOS
list. Everything llama.cpp reads out of a GGUF header has to exist in this repository
instead, per family:

- a **prompt transcription** (`core/common/.../model/<Family>Prompt.kt`), proved
  byte-equal against the family's real Jinja template by fixtures that
  `tools/executorch/render_reference.py` renders from upstream;
- **stop markers**, because the runtime streams end-of-turn tokens as ordinary text;
- **capability flags** — a format with no tool syntax (SmolLM2, Gemma 3) must not be
  offered tools, or the agent loop waits for calls that cannot come;
- a **recognition entry**, matched on the installed file's name with separators
  removed, refusing lookalikes (Qwen3.5, Gemma "4", Bielik) instead of guessing.

Adding an eighth family is those four things plus fixtures — roughly an afternoon, and
nothing in the engine changes. That is the extensibility story, and it held for seven.

## The suite, and why it is shaped like that

`ParitySuite` (on-device instrumentation) runs the same seven conversations on any
engine, greedy (temperature 0, topK 1), so a rerun after a backend change reproduces.
Cases are capabilities, not trivia: a trap question that punishes pattern-matching,
two-step arithmetic, a format constraint, extraction from a paragraph, memory across
turns fed back as the model's own raw reply (so the KV-cache path is the one tested),
and a tool call followed by its result. Multi-turn cases extend what the model actually
said, which is how the app stores history. Grades are regexes; every transcript is kept
in the JSON so the grades can be audited. Quantisations differ where the publishers'
do (a `.pte` is typically 8da4w, the GGUF counterpart Q4_K_M), so this compares
capability, not bit-parity.

## What the matrix caught (all fixed, each with the fix's test)

1. **The token budget was advisory.** The runner resolved a 768-token budget behind a
   405-token SmolLM3 prompt to 1643 and generated until the window filled. Only
   families whose stop markers surface as text ever stopped early — Qwen3 was being
   saved by its markers, not by the budget. The engine now counts generation callbacks
   (one callback is one token) and pulls `stop()` at the budget itself.
2. **Llama 3.2 ends a tool call with `<|eom_id|>`, not `<|eot_id|>`.** Without it in
   the stop list the model wrote the perfect call, the end-of-message token as text,
   and then a second turn explaining the call — and the explanation reached the parser.
3. **Llama emits calls behind `<|python_tag|>`**, its own tool-call token, which
   reaches the parser as literal text in front of clean JSON. On llama.cpp the native
   parser missed it too, so the fix in `ToolCallParser` repairs the family on both
   engines. The regression test is the verbatim reply from the device.
4. **No repetition penalty exists on this runtime.** SmolLM3, greedy, filled its
   budget with a control character after a tool result. Thirty-two identical
   consecutive tokens now cut generation; whole-word loops remain the model's own.
5. **A history grown past the export's fixed window** surfaced as a native
   `ExecutorchInvalidArgumentException` and killed everything after it. It is now a
   readable explanation ("start a new chat, or use a model exported with a larger
   window"), and the suite grades that failure per case.

## What the matrix says about the models (not the harness)

Final matrix (after every fix above; P pass, F fail, dash = family has no tool syntax),
cases in suite order — trap, arithmetic, format, extraction, memory, tool-call,
tool-result:

| Family | ExecuTorch | llama.cpp |
|---|---|---|
| Qwen3-1.7B | **PPPPPPP** | **PPPPPPP** |
| SmolLM3-3B | PPPPPFP | PPPPPFP |
| Llama-3.2-3B | FFPPPPF | FFPPPPF |
| LFM 2.5 1.2B | FFFPPPP | FFPPPPP |
| Gemma 3 1B | FFFPF-- | FFFPP-- |

- **Qwen3-1.7B is full parity, 7/7 on both engines**, including the complete tool
  loop. It is the reference model for the agentic path on the compiled runtime.
- **SmolLM3-3B is exact case-for-case parity.** The one shared failure is the tool
  call: both twins spend the budget thinking before emitting it, which is a property
  of SmolLM3's own system prompt on a phone budget, not of either runtime.
- **Llama-3.2-3B is exact parity** once its two format fixes were in — and both twins
  fail the same two arithmetic traps and both narrate *about* a tool result instead of
  using it, which is the model, reproduced faithfully twice.
- **LFM 2.5 1.2B**: identical failures on the two arithmetic traps (same weights, same
  rut); one divergence, the format constraint, where the 8da4w export answers in prose
  and Q4_K_M emits the JSON array — a quantisation delta, recorded.
- **Gemma 3 1B** fails the same three reasoning cases on both engines — the 1B is the
  1B — and its ET twin says "Bagis" where the GGUF says "Bagwis" on the memory case,
  the closest thing to a porting delta in the whole matrix and still a near-miss, not
  noise.

**No hallucination delta was observed in either direction**: on every case where the
engines disagree, the transcripts show the same kind of answer at different quality,
never a fabrication unique to one runtime.

## Answers the goal asked for explicitly

- **Python in the sandbox: no.** The execution tool is QuickJS in an isolated process;
  bundling CPython costs ~100 MB+ and a second attack surface for a marginal gain the
  JS sandbox already covers (parsing, filtering, arithmetic, large files).
- **Raw bash / external network calls: no.** A model-driven shell with network access
  is an unbounded exfiltration surface. The division of labour stays: `web_search`
  (ddgs) to find, `fetch_url` to read — now with `save_to`, so a page bigger than the
  context window lands in a file for the sandbox to work through — and `run_script`
  to compute. Each is individually gated and individually auditable.
- **Folder per chat thread: convention, not jail.** The tool preamble teaches one
  project folder per task. A hard jail would break the other half of the job — reading
  the files the user put in the shared folder for the model to work on.
- **Multimodal:** unaffected and unchanged on llama.cpp (vision and audio projectors);
  every published ExecuTorch text export is text-only, `mediaSupport` reports that,
  and the attachment button stays disabled for them rather than failing later.

## Security review (this change set's surface)

- Downloads: TLS enforced app-wide (`usesCleartextTraffic=false`), SHA-256 verified
  whenever the Hub reports one (all LFS weights). **Gap, accepted and recorded:**
  `tokenizer.json` is usually not LFS, so it arrives TLS-protected but hash-unverified,
  same as before this change.
- Hub-controlled names: installed file names pass through one sanitizer (dots kept
  interior, trimmed at ends; everything else dashed); paths resolve only by walking
  names the granted folder handed over, so `../` is inert by construction.
- The canvas server binds the loopback interface explicitly, serves GET only, resolves
  through the same workspace walk as every file tool, and its URL never leaves the
  device.
- Untrusted model output: tool-call parsing is format-anchored (a bare JSON object
  must be the entire reply); pages fetched from the web are flagged untrusted and gate
  anything that later leaves the device.
- Native parsing of downloaded files (`.pte` flatbuffers, tokenizer JSON) remains the
  largest untrusted-input surface, inherent to the feature and shared with the GGUF
  path; the mitigations are source choice (user-selected repos) and hash verification
  where the Hub provides it.
